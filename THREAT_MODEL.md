# Threat model

chard answers one question, which hardening flags your toolchain actually applied, by
compiling programs and reading what came out. That method decides this document: chard runs
your compiler with your privileges, and it reads binaries it did not build. Both positions
carry obligations, and neither is a claim of containment.

The short version: **chard is an instrument, not a boundary.** It is designed so that a wrong
answer is hard to produce and easy to detect. It is not designed to survive a hostile toolchain,
and confining a measurement run is the caller's job.

## What is defended

**A false `on`.** The property everything else serves. A cell reading `on` where the mitigation
is absent may stop someone investigating, so the design makes that outcome expensive: every
check is validated by a control triple before its verdict is used, and a probe that cannot
tell the flag on from off yields `probe-invalid` rather than a verdict.

**A false `off`.** The mirror, and the harder half, because absence of evidence reads so
naturally as evidence. Silence from a probe is never an answer: a check whose negative control
did not build, whose observable never appeared, or whose channel the toolchain does not
implement reports `probe-invalid`, `unsupported` or `indeterminate`, each distinct from `off` in
the schema's verdict enumeration.

**A report that is complete-looking but partial.** Every report carries a `coverage` block
counting checks handed in against observations emitted, because a check that never ran cannot
report its own absence. `--fail-on-missing` exits 1 for an incomplete run, separating "chard ran
and found problems" from "chard measured less than it should have".

**A report that contradicts itself.** Derived fields (the fortify ratchet, defect coverage, the
umbrella composites) are checked against the observations they were computed from, and the
`consistency` block records which rules ran as well as what they found. A contradiction is a bug
in chard, not a finding about your toolchain, so the report is written to
`<output>.contradicted` and the exit status is 3; two probes offering different facts under one
artifact digest are refused the same way. `table` and `matrix` refuse a report that contradicts
itself, and any file named `.contradicted`, `.previous` or `.partial`.

**An earlier report mistaken for this run's.** Every command given `-o` first moves a regular
file there to `.previous`, which a publication removes, so an earlier report outlives only a run
that did not publish, and then as `.previous`; a run refused before it moved anything leaves the
earlier file where it was. The output is written to a temporary file created exclusively, then
synced and renamed into place, or written in place with a note, not atomically, where the
directory refuses that; a writable file whose directory refuses the rename is copied to
`.previous` and emptied in place, so a failed run leaves an empty file there. A symbolic link at
`-o` is resolved when the run starts and its target replaced; a device, a FIFO or a link through
`/proc` such as `/dev/stdout` is written through. An output no run could publish to (a missing
directory, a directory, a link into nowhere, a name too long for the files written beside it) is
refused before measuring, with the earlier file in place; finding a name too long creates and
removes an empty file beside it, which a run killed between the two leaves behind. An input a
read command cannot read exits 2 with the earlier file intact, and when an input is read and
then refused under a rule, the earlier file at `-o` is set aside as above. `src/main.rs`
(`set_aside_output`) and `src/report.rs` carry the cases, among them which stale temporary files
are removed. Not covered: an invocation clap rejects, which exits before chard knows the path;
two runs sharing one `-o`, of which the last rename wins; and a writer in another pid namespace
or on another host sharing the directory, whose temporary file can be judged stale and removed.

**A verdict published without the evidence it came from.** Each observation carries the evidence
its detector consulted, trimmed to the hardening-relevant entries because the raw preprocessor
dump is thousands of lines. Trimming away something a detector read is silent: the verdict stays
right, and only a reader trying to check it finds the evidence insufficient. `_CXX_STDLIB` was
once trimmed while its fallbacks were kept, so every C++ hardening verdict on Linux was
published beside evidence that could not reproduce it. `tests/evidence_completeness.rs` and
`tests/predicates.rs` hold every name a decoder reads to the filter.

**A reading a third party cannot re-derive.** Every macro and elf-static reading, on the
measured build and on every control arm the triple evaluated, is published as a value
(`decoded`) naming the `facts` entries it was read from, beside the check's predicate in
`decoders`, so a third party can re-evaluate it from the report's JSON without chard's code
(`DESIGN.md`, "Proof objects and evidence by digest"). Each key a reading names is the digest
its own site published, so a reading moved to another arm's artifact is refused; the one key
bound by kind instead is an elf-static reading's macros taken from a preprocessor dump. `chard
detect <check> --evidence <report>` is that replay as a command: it exits 1 on a disagreement,
and names each reading it could not replay with its reason. It does not re-derive gating or the
fortify ratchet, so a measurement relabelled `indeterminate`, `unsupported` or `not-applicable`
is outside it; such a relabel withholds a cell rather than publishing a false `on` or `off`, and
`--fail-on-missing` reads an `unsupported` or `not-applicable` no gating rule reserves as
unsettled (`report::Observation::is_settled`). The runtime and compiler-diag readings replay
through this binary's decoder, which trusts the decoder source `run.decoders_sha256`
fingerprints; a predicate replay does not.

What this does not reach is the fact extractor itself: an ELF reader that misreads an artifact
publishes facts the predicate then reads faithfully. `tests/elf_readelf.rs` holds the reader to
`readelf` over real and generated objects; on a crafted file the two can differ, and the
crafted-ELF row of the attacker table ([below](#against-whom-and-under-what-assumptions)) names
the differences measured so far.

**Comparison of things that are not comparable.** Reports carry `probe_corpus_sha256`,
`harness_revision` and an execution mode, and `table` and `matrix` refuse to combine reports
that disagree on them. A report measured from a modified tree is named in every render, because
it corresponds to no commit and so cannot be cited; that is detected in a git clone, where git
says the tree is modified. A binary built from a `git archive` tarball
or a crate archive carries the commit its file names, and nothing checks the unpacked sources
against it (`archive-revision-names-the-unpacked-tree`); a revision asserted with
`CHARD_REVISION` is published as `asserted` and joins only reports asserted alike; and a
harness built under rustflags joins only reports built under the same flags
(`revision-and-rustflags-name-the-build`). A decoder change moves `probe_corpus_sha256`.

**Environmental perturbation of a measurement.** The compiler runs with a cleared environment
holding only the variables chard passes from its own (`PATH`) and `LC_ALL=C` and `TERM=dumb`
pinned, so a build-configuration variable, a loader variable such as `LD_PRELOAD`, or a variable
nobody has listed cannot reach it (`compile::COMPILER_ENV_PASSED`,
`compile::COMPILER_ENV_PINNED`). A toolchain configured through chard's own environment (a
wrapper reading a variable of its own, `GCC_SPECS`, a Nix cc-wrapper's `NIX_*`) is measured as
it behaves without that configuration: measured on 2026-10-11 with a stand-in wrapper that adds
`-fstack-protector-strong` only under a variable of its own, `canary-emitted` read `on` before
the clear and `off` after. A configuration is measured only when the invocation writes it, as
`--env NAME=VALUE`, and no value is ever taken from chard's own environment. `--env` refuses a
name chard passes or pins, so a pair cannot replace `PATH` or a diagnostic pin, and refuses a
value holding a relative path. Every report publishes the environment its toolchain received as
`profile.compiler_environment`, every pin and pair with its value (chard does not check a value
for a credential, so a credential does not belong in a pair), and a run with pairs carries their
digest in `profile.id`. chard does not notice that a toolchain reads a variable, only that its
dump or builds failed: a report without the pair gives no sign that one was needed, and a pair
the toolchain ignores is published as given (measured on NixOS 26.05: `NIX_HARDENING_ENABLE`
without the wrapper's role variable). A toolchain that cannot produce its macro dump without
some other variable is refused, exit 2 and no report (`compile::COMPILER_ENV_PASSED`;
`tests/fake_driver.rs`), and one whose dump works and whose builds fail without it publishes
those builds as `build-failed` (measured on 2026-10-11 with a stand-in whose builds fail without
`LD_LIBRARY_PATH`: no check read `off`). The variables listed next are kept from the driver like
any other, and named because each moved a measurement, or belongs to a family that does, were it
passed (`CFLAGS`, `CXXFLAGS`, `CPPFLAGS`, `LDFLAGS`, `CPATH`, `C_INCLUDE_PATH`,
`CPLUS_INCLUDE_PATH`, `LIBRARY_PATH`, `LD_RUN_PATH`, `GCC_COLORS`, `TMPDIR`, `TMP`, `TEMP`,
`TEMPDIR`, `COMPILER_PATH`, `GCC_EXEC_PREFIX`, `CLANG_NO_DEFAULT_CONFIG`,
`CCC_OVERRIDE_OPTIONS`, `LANG`, `LANGUAGE`, `LC_MESSAGES`, `HOME`, `MACOSX_DEPLOYMENT_TARGET`,
`IPHONEOS_DEPLOYMENT_TARGET`, `TVOS_DEPLOYMENT_TARGET`, `WATCHOS_DEPLOYMENT_TARGET`,
`XROS_DEPLOYMENT_TARGET`, `DRIVERKIT_DEPLOYMENT_TARGET`, `RC_DEBUG_PREFIX_MAP`,
`RC_DEBUG_OPTIONS`, `SDKROOT`, `GCC_COMPARE_DEBUG`, `GCC_EXTRA_DIAGNOSTIC_OUTPUT`, `GCC_URLS`,
`GCC_DIAGNOSTICS_LOG`, `EXPERIMENTAL_SARIF_SOCKET`, `LDEMULATION`, `GNUTARGET`,
`COLLECT_NO_DEMANGLE`, `SOURCE_DATE_EPOCH`, `LPATH`, `GCC_ROOT`, `BINUTILS_ROOT`,
`DEPENDENCIES_OUTPUT`, `SUNPRO_DEPENDENCIES`, `CC_PRINT_OPTIONS`, `CC_PRINT_HEADERS`,
`CC_PRINT_HEADERS_FILE`, `CC_PRINT_HEADERS_FORMAT`, `CC_PRINT_HEADERS_FILTERING`,
`CC_LOG_DIAGNOSTICS`, `CC_LOG_DIAGNOSTICS_FILE`, `CC_PRINT_INTERNAL_STAT`,
`CC_PRINT_INTERNAL_STAT_FILE`, `CC_PRINT_PROC_STAT`, `CC_PRINT_PROC_STAT_FILE`,
`FORCE_CLANG_DIAGNOSTICS_CRASH`, `CLANG_CRASH_DIAGNOSTICS_DIR`, `CLANG_MODULE_CACHE_PATH`).
`compile::COMPILER_ENV_NAMED` holds that list, `tests/register.rs` holds these sentences to it,
`COMPILER_ENV_PASSED` and `COMPILER_ENV_PINNED`, and the comment on the list records which moved
a measurement and on which host (the driver-side entries on Fedora 44 with gcc 16 and clang
22.1.8). Where a Darwin triple leaves the minimum version to it (no `-mmacosx-version-min=`, and
not the versionless `arm64-apple-macosx`), `MACOSX_DEPLOYMENT_TARGET` moves the compile triple
and the macro dump (clang 22.1.8's Darwin driver on Fedora 44 x86_64), and on Apple clang 21 it
moved every macro-dump digest of a report with no verdict moving; Apple clang 21.0.0 on arm64
macOS builds and links a C program with the Darwin entries absent. A host that needs another SDK
or target names it in an `explicit` profile (`-isysroot`, `-mmacosx-version-min=`), which the
report records. A probe runs with no ambient variable at all: `run::execute` clears the
environment and sets exactly `LC_ALL=C` and `LIBC_FATAL_STDERR_=1`, so `LD_PRELOAD`,
`GLIBC_TUNABLES`, the `*SAN_OPTIONS` and any loader variable nobody has listed cannot reach it.
One probe adds a pin of its own: `shadow-stack` runs every arm with
`GLIBC_TUNABLES=glibc.cpu.hwcaps=SHSTK:glibc.malloc.perturb=170`, glibc's opt-in to the x86
shadow stack, because glibc 2.39 and later enforce none without it; the second tunable is the
pin's own witness, and the check reads `on` only where a second run without the opt-in was
enforced too (`probe::Probe::run_environment`). Each run record carries what the probe received
as `environment`, so a runtime verdict can be re-derived under the same conditions. chard's CLI
takes no configuration from the environment beyond `PATH`. Core files are outside this clearing,
as the section below says.

**A probe's account of how it died.** The wait status chard reads carries the signal a probe
died by and nothing else. A compiler's trap is `SIGILL` or `SIGTRAP` on x86 and `SIGTRAP` at
`brk` on aarch64, and on aarch64 an undefined instruction, a BTI fault and, on a CPU with
`FEAT_FPAC`, a PAC authentication failure arrive as `SIGILL` too, which the bare signal cannot
tell from a trap and credits as one; the comment on the reporter in `probes/chard_selfreport.h`
records the measurements, and `ud0` and i386 were not measured. A probe built with
`CHARD_WANT_FAULT_REPORT` installs a reporter, which on Linux (aarch64, x86_64 and i386) catches
(`SIGILL`, `SIGTRAP`, `SIGSEGV`, `SIGBUS`), writes one line to the probe's stderr and then dies
by the signal it took: `chard-fault-v1` followed by its fields (`signal`, `code`, `sent`,
`arch`, `pc`, `addr`, `word`, `esr`, `at-target`). Elsewhere it installs nothing. The line is
the probe testifying about itself, and it is trusted for one thing: telling those faults apart
once the run record has established the death. A report is read only whole, only from the last
`chard-fault-v1` line on stderr, and only when its signal is the signal the run record says the
probe died by. A probe can write the prefix itself, which is why only the last line counts; the
probe sources are chard's own, inside the trust boundary with the compiler. `RunRecord::trapped`
counts a death as a trap only where the bare signal (`SIGILL` or `SIGTRAP`) would, so a report
can remove trap credit and never add it. Removal is the direction that could read `off` where a
trap fired, so a check that opts a probe in reads `RunRecord::fault` instead: for a death by a
caught signal, a missing report and an undecided one (`Fault::Undetermined`) must withhold the
reading rather than read `off`, as must a run on a system where the reporter installs nothing.
No probe in the corpus opts in yet, so no verdict reads the line; a check that opts a probe in
must hold that withholding with its own test, and the probe is named here by its id.
`tests/register.rs` holds this paragraph to the reporter and to `run::FaultReport`.

**Memory safety in the one place untrusted input arrives.** `chard elf` and `chard detect
--artifact` read binaries chard did not build; the second prints a detection, never a verdict.
The ELF reader is safe Rust over a byte slice under `unsafe_code = "deny"`, with no binding to a
C library and no shelling out to `readelf` or `objdump`. A single object above 512 MiB is refused
rather than read, and the reader is fuzzed against corrupted real objects. An object the reader
declines is reported in the error envelope as the caller's input; a panic above `Cursor` is
chard's bug. A table the reader could not finish is a typed truncation, and a check reading it
is withheld under `artifact-unreadable`. Kani proves `Cursor`'s bounded reads (`slice`,
`u16_at`, `u32_at`, `u64_at`, `addr_at`) total over a bounded buffer with *unbounded* symbolic
offset and length: each returns for every input, a successful read is exactly the width asked,
and every refusal is classified (`make kani`; [`proofs/`](proofs/)). `Cursor`'s sixth method,
`cstr_at`, bounded to its caller's declared table length, is held by a unit test instead
(`a_cstring_read_never_crosses_its_own_tables_declared_end`), since a Kani proof over its
`memchr` path timed out at 480s (`src/elf.rs`, `ReadError`). None of this keeps the reader from
reading a file differently from the loader; the crafted-ELF row of the attacker table says what
it does not cover. [`proofs/README.md`](proofs/README.md) says what each harness proves and
what a test over its whole domain holds instead.

## Against whom, and under what assumptions

The attacker positions this design takes seriously:

| position | what they control | what stops them producing a wrong verdict |
|---|---|---|
| A crafted ELF file | the bytes `chard elf` and `chard detect --artifact` parse | **a crash and an unfinished table; the misreadings named below are not stopped.** The memory-safety paragraph above says what stops a crash; a panic above `Cursor` is still a bug to report. Nothing stops a file the reader reads in full but differently from the loader or binutils `readelf`, and a check read from such a file can publish a wrong verdict, or `chard detect` a wrong detection. The register below names the readings of that kind measured so far, each with what retires it: [`property-note-name-size-is-four`](#property-note-name-size-is-four), [`property-word-lies-in-its-descriptor`](#property-word-lies-in-its-descriptor), [`feature-word-is-four-bytes`](#feature-word-is-four-bytes), [`dynamic-symbol-names-carry-no-version`](#dynamic-symbol-names-carry-no-version), [`address-reached-tables-lie-in-the-file-image`](#address-reached-tables-lie-in-the-file-image), [`note-segments-align-to-four-or-eight`](#note-segments-align-to-four-or-eight), [`one-property-note-per-object`](#one-property-note-per-object). That a reading is not named there is no evidence that the reader refuses it. These readings hold for any ELF chard reads, a toolchain's own output included: the malformed feature word was measured in clang 7's output. A file that is well formed and false, such as a symbol added by hand, is read as it says, and nothing here defends against it |
| A redirected toolchain, behaving the same for every build | a wrapper earlier on `PATH`; the driver's own redirecting variables are cleared (the environmental-perturbation paragraph above) | the control triple. The controls are built through the same redirection, so a compiler that no longer responds to a flag stops showing the observable in the positive arm, and the check reads `probe-invalid` rather than a fabricated `on`. The linker's `--version` banner is held to the `.comment` an lld or mold link signs every artifact with, and a banner naming another linker or version reads `disagrees` with an error diagnostic; a `bfd` or `gold` banner is uncontradicted and confirmed by nothing. A driver or linker query that failed is not read, whatever it printed. The target `-dumpmachine` reports is held to every artifact's `e_machine` and to the driver's macro dump, and an arch-gated check whose gate they decide otherwise is withheld under `target-arch-contradicted` (`DESIGN.md`, "The binary testifies about itself"). A wrapper that rewrites the `-dM -E` output as well as `-dumpmachine` defeats the dump, and only the artifacts remain. |
| A redirected toolchain that recognises which build it is compiling | the same, plus chard's variant naming, which is public | **the macro channel's twin rule, and nothing for the artifact channels.** A macro reading whose artifact or runtime twin read the opposite presence is withheld under `macro-contradicted-by-artifact` (`DESIGN.md`, "Verdict vocabulary"); a reading of an artifact the wrapper hardened is a true reading of that artifact and stands. Measured under `bare` with gcc 16.1.1 on Fedora 44 x86_64 (GNU ld 2.46.1, glibc 2.43), against the same run without the wrapper. The wrapper, for `gcc` and `g++`, adds `-fstack-protector-strong -fPIE -pie -Wl,-z,relro,-z,now` only when `-o` ends in `-clean` or `-measured`, and passes control arms through untouched. Against the unwrapped `bare` run it moves seven readings from `off`/`partial` to `on`, each with `discriminating: true` and `confidence: high`: `ssp-level`, `pie-macro` and `pic-macro` on the macro channel and `pie`, `relro`, `canary-emitted` and `ssp-covers-small-arrays` on the artifact. `relative-relocs` also moves, from `not-applicable` to `off`, since the build it reads becomes a PIE. In the `toolchain` block, `id` and `predefined_macros_sha256` are byte-identical, because `-dM -E` carries no `-o` to key on; only `driver` and `cxx_driver` differ, paths that `table`, `matrix` and `digest` do not print. Without the twin rule the report shows only a trace: `ssp-level-emitted` stays `off` beside `ssp-level` `on`, so `table` draws stack-protector as `!off/on`; `diagnostics` carries a channels-disagree error on stack-protector, and two warnings that the compiled code and the macro dump disagree about `__PIC__`, `__PIE__` and `__SSP_STRONG__`. None of that trace withholds a verdict: the seven publish `on`, beside an error whose text says such a verdict should not be published, and `measure` exits 0. Under the twin rule the same run reads `ssp-level` `indeterminate` under `macro-contradicted-by-artifact`, the reason naming `ssp-level-emitted` `off` as the reading that contradicts it and `canary-emitted` `on` as the one that agrees, with a warning in `ssp-level`'s context; the other six keep their `on`, the four artifact readings because they read artifacts the wrapper hardened, and `pie-macro` and `pic-macro` because their twins were hardened too (`pie` `on`; `pic-object-relocs` `off`, consulted for an absent reading only); the stack-protector group's note says `ssp-level` was withheld and that its other members, `canary-emitted` beside `ssp-level-emitted`, disagree among themselves (two readers of two artifacts the wrapper treated differently), under an error diagnostic; the macro dump warning remains; the exit status is 0. The rule holds a macro reading only where a twin measured: a run that selects no twin probe publishes the macro reading beside the coverage warning, and a wrapper that drives every twin to a withheld verdict publishes it with no warning of its own. The artifact readings are the "operator chose the toolchain" assumption below, not something the triple covers |
| A macro level forged inside a present reading, a forged `fortify-effective` or `optimization-enabled`, or a probe steered by a macro the list never named | the same inputs as the twin rule's row above | **nothing beyond the corroboration group's note.** The twin rule compares presence, not levels: `cet-macro` `on` at `full` beside `cet-marked` `partial` at `branch` is an honest link whose startup objects carry no shadow-stack bit (2 of 311 fleet reports, OpenBSD `openssf-tldr`), and `pie-macro`'s level is a code model; so a `__SSP_STRONG__` reaching the measured build alone under a real `-fstack-protector` (a `-D` in the list is the spoof rule's; the carrier is a wrapper that recognises the build, a forced include or a selected header) reads `ssp-level` `on` at `strong` beside `ssp-level-emitted` `partial` at `basic`, published under the group's `LEVELS DISAGREE` note (measured with gcc 16.1.1 on Fedora 44 x86_64, `--profile explicit --flags "-O2 -fstack-protector"` through a wrapper adding `-D__SSP_STRONG__=3` to the build whose output name ends in `-measured`). `fortify-effective` and `optimization-enabled` have no twin (`report::MACRO_WITHOUT_TWIN`): the first's runtime rungs diverge from it honestly under fortify-headers and on FreeBSD, and no artifact reads the optimiser's state, so a level forged into the self-report beside rungs reading `off`, or a forged `__OPTIMIZE__`, publishes. Measured with gcc 16.1.1 on Fedora 44 x86_64, each over arms that discriminated and each `indeterminate` under the rule: `--profile explicit --flags "-O0 -DGATE -include h"` with `h` defining `__OPTIMIZE__ 1` under `GATE` read `optimization-enabled` `on` over an unoptimised build, `-O2 -DGATE -include h` with `h` undefining it read `off` over an optimised one, and `-O0 -DGATE -I<dir>` with the directory's `stdc-predef.h` including the next one and defining the macro under `GATE` read `on`. The same header keyed the same way on `__CET__`, `__EXCEPTIONS` or another twinned macro is held by the twin rule above; a level it forges inside a present reading is the residual this row opens with. What remains for the two: a wrapper adding the define to the measured build alone, and a shadow header under a path word the target or runtime selection carries to every arm (`--sysroot`, `-isysroot`, `-B`, `--prefix`, `--gcc-toolchain=`, `--gcc-install-dir=`, a resource directory), which the clause does not read; a header keyed on a macro a hardening flag the arms do not carry implies (`__PIE__` under `-fPIE`) reads the build the profile makes. The route corpus (`tests/route_corpus.rs`) leaves the wrapper and the path words out, as a driver and a toolchain layout rather than a spelling, and an artifact twin for `optimization-enabled` (a dead static the optimiser removes) would hold that check on every carrier at once. The probes whose source branches on a reserved macro (`measure::PROBE_MACRO_BRANCHES`) are withheld where the list names the macro, carries an input that can, or where the driver's listing for the measured compile differs from the arms' (a `-specs=` or `--config=` file's macro operations); a header the profile selects by `-I`, `-isystem`, `-idirafter` or `-iquote` that defines the macro (a shadow of a system header the probe includes, reachable from the profile's own list since the arms carry those words), or under such a directory handed to the preprocessor (`-Xpreprocessor -I`, `-Xpreprocessor -isystem`, `-Wp,-I`, clang's `-Xclang -I`), which no arm carries and which clang's `no-strict-overflow` and `no-strict-aliasing` read through as through the driver's word, or a wrapper that adds the define to the measured build alone, steers such a probe's runtime and artifact readings unseen, and they have no twin; of them the three compile-input readings (`strict-flex-arrays-enforced`, `cxx-stdlib-assertions`, `cxx-assertions-symbol`) are withheld under `macro-supplied-by-profile` wherever the list selects one (`measure::settle_probe_branches`), and the others publish under a directory word. The route corpus (`tests/route_corpus.rs`) runs those directories, the driver's and the ones handed to the preprocessor, and names each of their readings that still publishes among its open routes (clang's `no-strict-overflow` and `no-strict-aliasing` under a shadow `__OPTIMIZE__`); it leaves the wrapper out |
| A spec file that lies | what `cc -dM -E` prints versus what the compiler emits | the macro channel reads the section the compiler wrote into the artifact, and a macro check whose artifact gave no account of its macros is withheld under `artifact-lacks-self-report` rather than read from the dump (`DESIGN.md`, "Verdict vocabulary"). A driver that removed the section after each link shows why: measured on Fedora 44 x86_64, gcc 16.1.1, the dump alone read six macro checks of `toolchain-macros` `off` and one `on`, and with `-fstack-protector-strong` handed to the `-dM -E` job alone `ssp-level` read `on`, level `strong`, beside `canary-emitted` `off`. A section a tool rewrote is read as the artifact's account: the redirected-toolchain position, defended by nothing. On a macOS run the dump is read by design where the reader refused the artifact as a Mach-O object, the format its probes are built in, and this position is not defended for that reading; every other refused artifact, and a build that wrote none, is withheld on every host. A control arm that lost its section is a dump reading, disclosed by its own `macro_source` (the register's `self-report-absent-withholds-the-macro-channel`). |
| Whoever hands you the report | the JSON itself, after `measure` wrote it | **nothing cryptographic.** A report is not signed and carries no hash of itself, so a reader who did not run chard cannot establish that it is the file that was produced. Integrity in transit is the caller's: sign it, or obtain it over a channel you trust. The readers check less, as the next section says: copies of each verdict held to each other, and derived blocks re-derived on read. An editor who changes every copy defeats both. |
| A stale or mixed dataset | which reports get rendered together | corpus hash and harness revision are join keys; mixing them is refused, and `--allow-mixed` puts the conflict into the output where redirecting cannot lose it |

### What a reader checks of a report it did not write

Each verdict appears more than once: in `observations`, in the `composites` constituent naming
that check, and in the report's first key, `digest`. `table` and `matrix` refuse a report whose
copies disagree, or whose `consistency` block is missing, contradicted or inconsistent with
itself, and `digest` refuses a digest the rest of the report does not give. That catches an
edit that touched one copy, a truncated or merged file, and a report assembled by hand.

The rules in `report::REREAD_RULES` are re-run on read through the functions `measure` calls, so
an edit to a derived block alone is refused naming its rule. They are, by id:

- **The kernel and the C library are honest** about what they enforce. chard reads artifacts, and

- **The operator chose the toolchain.** `--cc /path/to/gcc` is a documented option, and pointing

- **The build host is not already compromised.** chard cannot distinguish a hardening flag that is

The table is the count. `tests/register.rs` holds every entry in `report::ASSUMPTIONS` to a row
of the table and every row to an entry, and the row count to the entry count
(`every_register_row_is_a_shipped_assumption`). An entry leaves in one of three ways, and how it
left is worth keeping: **retired by measurement**, by measuring the thing it was about;
**retired by mechanism**, where a reader checks the assumption on every artifact and
withholds where it fails, as `elf::code` reads each relocated field in a function before
searching it and `env::runs_natively` holds an artifact's byte order to the kernel's; or
**removed** with the code that held it, which answers nothing. Two removed entries transfer
rather than vanish: whoever assembles a flag list for `--profile explicit` inherits "a query
exiting 0 answered from every source it should have", and anything comparing two images by path
still needs an identity better than the basename.

Removing the code that holds an assumption removes the assumption from *this* tool; it does not
answer the question, and in those two cases the question belongs to whoever does the equivalent
work.

`noexecstack-enforced` withholds every reading it does not recognise (a fault elsewhere, a
`SIGILL`, a return other than its marker, an unclean exit), so the kernel behaviour it reads is
what it measures; only its negative control's loader refusal rests on an entry,
`loader-refusal-is-the-execstack-refusal`. On OpenBSD, which `openbsd-environment-unobserved`
covers, chard cannot see whose kernel it runs on, so a check that declares `needs_vm` is
withheld under `execution-mode-assumed` unless the operator passes `--execution`. OpenBSD has no
container runtime whose kernel belongs to someone else, and a vmm guest runs its own kernel, so
there the operator's word settles it, not an observed fact, and `openbsd-environment-unobserved`
stands.

## What is explicitly not defended

**chard is not a sandbox, and running it does not confine anything.** It compiles and executes
probe programs from its embedded corpus, using your compiler, with your privileges. Some runtime
probes work by crashing. On Linux each probe that dies by its own crash makes itself
non-dumpable first, so the kernel writes no core and hands nothing to a pipe `core_pattern`'s
helper; where that fails, or off Linux, a run leaves core dumps wherever your system collects
them, and a direct `chard measure` runs under your own core limit (`make sweep` lowers it to 0).
What a toolchain you would not otherwise run does when chard runs it is the toolchain's doing.
**Confining a measurement run is the caller's job**: a container, a VM, or a dedicated build
user. Nor does chard establish from inside whose kernel it runs on: it takes the operator's
`--execution`, refuses it where it sees a container, and where no word was given withholds the
checks that declare `needs_vm` (the register entry `asserted-mode-names-the-kernels-owner`;
`DESIGN.md`, "Containers vs VMs").

**A hostile compiler wins.** The compiler under test is inside the trust boundary, not outside it.
A toolchain built to detect chard's probes and emit hardened code only for them would produce a
clean report, and no control-triple validation reaches that, because every arm of the triple
goes through the same compiler. chard measures a toolchain that is merely *misconfigured*.

**The work directory claim is not a lock against anyone.** `measure` claims its work directory
so that two of its own runs never share one by accident. A process that can write the directory
can remove or forge a claim, and another user who can write it can plant one that refuses
every run; keeping other writers out of it is the caller's job.

**A verdict is about the artifact, not about the running system.** `pie: on` is a statement about
`ET_DYN`, not about address randomisation, and the `boundary` field says what else must hold.
The two checks that run a program and read what the kernel did, `noexecstack-enforced` and
`shadow-stack-enforced`, are properties of the measuring host's kernel and CPU with a program
this toolchain linked, not of every system the binary may run on, and each `boundary` says so.
`shadow-stack-enforced` reads `on` only where the shadow stack was enforced without glibc's
opt-in, and `partial` at `opt-in` where only with it.

**chard does not measure your build.** It measures how your toolchain responds to chard's probes.
Your own Makefile, a vendored dependency or a submodule's flags can still weaken the result.
`--profile explicit --flags "$CFLAGS"` measures the flags passed to it; it does not see a flag
your build adds elsewhere.

**A withheld verdict is not a gap.** `probe-invalid` and `indeterminate` mean the evidence did
not support an answer, and refusing to guess is the point of the control triple. `unsupported`
and `not-applicable` are settled rather than withheld, each with the rule that established it,
so a complete run can still contain them. The sharpest case is `zero-init-padding-bits`. Measured
on Fedora 44 x86_64 under `bare`, `bare-optimized` and `openssf-tldr`, it
answers on gcc 16.1.1 under `bare` alone, where it reads `off`. In clang 22.1.8's three cells it
reads `unsupported`, since clang has no such option. In gcc's two cells at `-O2` it is withheld
as `indeterminate`. The probe fills a stack frame with 0x5a, re-enters it, and reads whether a
union's padding byte comes back zeroed. At `-O2` the opted-out control read 0x1a and 0x00
rather than 0x5a, so the frame was not reused as the probe needs. The padding byte's 0x00 there
looks like the flag working and establishes nothing.

**Incomplete coverage is not a defect.** The corpus reads fewer flags than the OpenSSF guide
recommends, and `chard probes` lists what it measures. Every detector has recorded evidence,
from x86_64 and aarch64 runs between them, which `tests/detector_replay.rs` holds; recorded
evidence is not a proof.

**chard cannot tell an upstream default from a distribution patch.** gcc's
`-Werror=implicit-function-declaration` and a specs patch setting the same thing look identical
from the artifact.

**A report names the paths it was given.** `run.invocation` records each argument as the
operator passed it, so the values of `--workdir`, `--output`, `-o` and `--image-attestation` are
published as written, including any home directory in them; `--normalize` replaces each value
with `<normalized>`, and `argv[0]` is recorded as the text after its last `/`. The `--cc` value,
any path inside `--flags`, `--cxxflags` or `--ldflags`, and the paths of the toolchain that ran,
wherever the report quotes them (among them `toolchain.driver`, `toolchain.cxx_driver`,
`toolchain.linker.path` and the first `argv` entry of every build record), are part of what was
measured, and are published with or without `--normalize`. So is the description of the
measuring host, which can name it: the kernel release string with any local version suffix, and
an image attestation's content. Publishing a report publishes all of these.

**Supply chain.** chard has four direct dependencies, no build-dependencies and no
dev-dependencies; `Cargo.lock` lists the whole graph, and `deny.toml` pins the licence, ban and
source policy against it (`make check`). That bounds what enters the graph; chard makes no
claim about the crates in it beyond naming them.

## Reporting

What is defended above is what a report to chard may be about: a false verdict in either
direction, a `coverage` block that calls a partial run complete, a `discriminating` flag that was
not earned, a panic in the ELF reader. [`SECURITY.md`](SECURITY.md) says how to report
privately something you believe is a vulnerability; anything else is an ordinary issue.
